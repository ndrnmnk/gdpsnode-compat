# Legacy Geometry Dash compatibility

This plugin adapts the older GD protocols used by the supplied GMDprivateServer PHP implementation to GDPSnode. All implementation, restored endpoints, documentation, and tests live in this directory. It needs no additional npm packages and does not run or require the PHP server.

## Enable

Keep the entire `legacy-compat` directory under GDPSnode's `plugins/` directory and restart GDPSnode. Plugins are enabled by default; if you have disabled them, set `ENABLE_PLUGINS=1` in your existing deployment configuration. If you use a custom `PLUGINS_DIR`, place this directory there instead.

Point clients at the same server URL as current clients. Older endpoint names are rewritten internally, preserving the POST body and query string. Redirect support is not required; credentials never go into a redirect URL.

## Implemented protocols

| Area | Compatibility behavior |
| --- | --- |
| Routing | Original, `19`, `20`, and `21` level, comment, score, like, rating, map pack, gauntlet, creator, report, and account backup/sync route names map to their current equivalents. See `aliases` in `index.js` for the exact list. |
| Accounts | Plain password login and legacy base64/XOR `gjp` become `gjp2`; core handlers still verify the resulting credential. Old registration requests do not need `rsession`. Login and registration requests containing a plaintext `password` field require HTTPS for every game version, including modern registration; HTTP requests receive `-1` before credential lookup or account creation. Hash-only login retains the core transport behavior. |
| Guests | Pre-account clients can update scores, upload levels/comments, vote, and request relative/friends leaderboards using `udid`. A persistent device mapping gives each guest a separate internal account/profile with a random credential. For pre-2.2 interactions, placeholder `gjp`/`gjp2` values are ignored when `accountID` is absent or zero; positive account IDs always require valid credentials and never fall back to a guest. This also supports signed-out 2.1 level uploads. Claimed `userID` values never authenticate registered accounts. |
| Guest names | Incoming guest names update the public profile without changing the internal credential name. Creator strings and comment profiles use that display name, retain a nonzero user ID, and report account ID zero (comment profile key 16), enabling green unregistered names. This response normalization also applies when a current client views guest uploads. Guest score/user listings use the same public identity. |
| Deletion | Original/19 comment and level-deletion paths map to the core routes. Anonymous deletion resolves an existing UDID mapping and keeps native ownership/moderation checks; it never creates a guest for an unknown deleting device. Level deletion requires `Wmfv2898gc9`; comment deletion requires the common secret. Old account-comment deletion requests default their omitted target account to the authenticated caller. Rated-level restrictions and related-data/file cleanup remain in core. |
| Levels | Raw pre-1.9 data and 1.9 zlib data become gzip for core storage. Downloads return raw data to pre-1.9 clients, compressed data to newer clients, and plain descriptions/copy passwords before 2.0. Hashes cover the transmitted level string. |
| Search | Old clients see levels at or below their game version, excluding platformers. Filtering happens before counts and pagination, and also applies to direct downloads, map packs, and gauntlets. Newer level objects are not converted into old objects. |
| Gauntlets | Legacy `getGJLevels21.php` requests with `gauntlet` load the five configured levels, retain their configured order, attach field 44, and recalculate the level-list hash. Unknown, incomplete, private, disabled-owner, platformer, and newer-version entries are rejected rather than returning a partial or unrelated list. Listing and level downloads work with anonymous and authenticated requests. |
| Daily rewards | Logged-out legacy `getGJRewards.php` requests use the UDID guest mapping for saved chest timers and counts instead of trusting placeholder `uuid=1`. Core chest validation, configured rewards, and cooldowns are reused. The response keeps account ID zero, returns the real guest player ID, echoes the nonce, and uses the PHP-compatible legacy envelope and hash. Registered and modern requests retain their original response behavior. |
| Quests | Legacy `getGJChallenges.php` returns the PHP-compatible `SaKuJ` payload, nonce echo, XOR/base64 encoding, and salted hash. Registered accounts still authenticate through converted GJP; anonymous identities retain account ID zero. Configured valid quests are used; missing entries are filled with default orb/coin/star quests without writing to the quest table. Selection, IDs, and expiry remain consistent within a UTC day. Modern 2.2 requests keep using the core handler. |
| Comments | Pre-2.0 text is encoded on upload and decoded on download. Pre-2.1 responses have a separate author section; 2.1 responses have inline profiles. Old upload checksums are adapted to the current handler. |
| Votes | `rateGJLevel.php` maps faces 0–6 to star votes 1/2/3/4/6/8/10 (including auto and demon). The 2.1 `rateGJStars211.php` and `likeGJItem211.php` routes support anonymous device identities, with an IP fallback for votes that omit a device ID. The 2.0 `rateGJStars20.php` route accepts its `stars` field and supports anonymous IP/device identities with the common secret. The 1.9 `rateGJStars.php` route maps its `rating` field directly to 1–10 star votes, requires the common secret, and supports anonymous IP/device identities through the core rating handler. Original `rateGJLevel.php`, `likeGJLevel.php`, and `likeGJItem.php` requests before 1.9 may omit the secret and device ID. Without a device ID, the identity is keyed to Express's client IP. Anonymous legacy item-vote requests, including 2.1 `likeGJItem211.php`, update the shared level/comment counters directly, following the PHP reference's allowance of three actions per identity and item. Each accepted like adds one and each accepted dislike subtracts one, including repeated actions from the same identity. Existing native increment markers count as one historical action, so old votes are preserved without silently blocking the next dislike. Authenticated pre-2.2 level/comment item votes use the same three-action allowance keyed to the verified account; their existing native vote marker counts as the first action. Invalid credentials and disabled accounts are rejected before counters change. `likeGJLevel.php`, star/face ratings, and modern 2.2 item-vote requests retain their existing core deduplication rules. Explicitly incorrect secrets are still rejected. |
| Scores | Old relative/friends requests resolve their `udid` to the persistent guest profile. Pre-1.9 top leaderboards include zero-star players so new profiles render before earning stars; modern leaderboards retain their original filter. Missing later-version stats/icons are preserved. Existing demon/star/platformer summaries are retained when old clients submit profile updates. |
| Friend requests | Classic clients use `frS=0` for all requests; core uses `frS=0` for no-text requests and `frS=2` for requests with text. An authenticated pre-2.2 settings update selecting all is translated to 2, and profile responses translate 2 back to 0 for classic clients. Existing recipient settings are not changed merely by receiving a request. Blocks, duplicate checks, and friend limits remain in core. |
| Messages | The four removed handlers are restored locally. Legacy users can send/list/read/delete messages in the existing `messages` table. Listing preserves unread status; downloading marks a received message read. Blocks, friends-only settings, disabled accounts, ownership, and the no-messages setting are enforced. Legacy profile unread counts use this inbox. |
| Backups | Old account paths and username/password authentication work with the current backup/sync handlers. Missing modern request metadata is supplied, and sync's version trailer matches the requesting client. |

Requests with modern `gameVersion=22` and `gjp2` continue through core handlers, including current inbox read behavior. Public guest names/account IDs are normalized on level, comment, score and user responses for modern clients too. The restored upload/delete message routes are also available with modern credentials. The plugin uses `AsyncLocalStorage` and database hooks to keep version filters and score preservation scoped to each request.

HTTPS is determined by Express's `req.secure`. Direct TLS works without proxy configuration; HTTPS terminated by a reverse proxy uses GDPSnode's existing `TRUST_PROXY_HOPS` / `TRUST_PROXY` setting. A raw `X-Forwarded-Proto` header does not bypass the plugin's guard unless Express has already accepted it from a trusted proxy. Blocked HTTP account requests are rejected without redirects.

Version detection uses `gameVersion`, then the historical endpoint suffix. `gameVersion=20, binaryVersion=29` is 2.01 and remains version 20 for storage, checksums, searches, and downloads. Only binary versions 30 and above are treated as early 2.1/World when they still report `gameVersion=20`; the PHP reference's older `>27` heuristic incorrectly promotes 2.01. The unversioned `rateGJStars.php` route defaults to 1.9. Other unversioned original route names default to pre-1.9; unchanged endpoints with `gjp` default to 2.1 when no version was provided. Supplying the client's actual version removes that ambiguity.

## Persistence and boundaries

The plugin creates `legacy_compat_guests`, mapping a hash of the device ID to its internal account, and `legacy_compat_like_counts`, counting accepted anonymous item-vote actions. The second table is created automatically on restart; it does not reset existing likes or native vote markers. Guest accounts/profiles otherwise use core tables and normal core level storage. Account 72 remains reserved for the first real registration, preserving GDPSnode's initial moderator setup even when guests arrive first. Clients behind a shared IP share the anonymous voting identity when no device ID is sent; proxy deployments use GDPSnode's existing Express trust-proxy setting. Guest identities otherwise have the same device-ID trust model as historical unsigned clients; they cannot be upgraded into registered accounts by this plugin.

A pending friend request in either direction prevents sending another request between the same accounts. The sender can accept or decline the existing incoming request; changing message privacy does not remove it. When comparing clients, test the same sending direction with the same recipient policy and no existing request. The sender's `mS` does not affect `uploadFriendRequest20.php`.

A recipient with stored `frS=0` accepts empty friend requests only; choose all/text-enabled requests in their settings to accept a request with text. Legacy message `mS=1` is friends-only and `mS=2` disallows messages, including from friends. A valid 2.0 payload is still rejected if that recipient policy is not satisfied.

Legacy messages and current thread conversations remain separate. There is no automatic migration between them, and legacy messages do not generate thread notifications. Existing core bans, validation, rate limits, and permissions still apply. Uploads with the same owner/name update the existing level and return its ID, as in core; a different name creates a new level. Re-uploading a 2.01 level with its original name also repairs a version-21 tag left by the older plugin. Genuine 2.1 levels are not globally downgraded. Cross-version cloud saves share the core save slot; the plugin does not translate save contents or downgrade newer game data. The core's existing body-size limits also apply to aliased requests.

Removing this directory disables the compatibility layer. Existing guest profiles, levels, and messages remain in the database; removing the mapping table would make those device identities unreachable, so retain it if you plan to re-enable the plugin.

## Verification

From the GDPSnode directory:

```sh
node plugins/legacy-compat/test/compat.test.js
```

The suite uses Node's test API, the real core endpoint modules, the real core schema, and SQLite through Python 3's standard library. It dispatches middleware/routes in-process and redirects all level-file I/O to a temporary directory. It does not require installing Express or better-sqlite3, start the full server, or modify files outside the test's temporary directory.

Coverage includes the captured 2.0 friend-request/message payloads, classic privacy-setting round trips, paired opposite-direction 2.0/2.2 requests with reverse pending-request handling and sender-message-setting independence, no-text/friends-only/no-messages settings and blocks, green guest names on old/current clients, nickname changes, 2.1 guest comment checksums, captured guest deletion routes, cross-device ownership and rated-level restrictions, omitted account-comment targets, core file/data cleanup, the captured logged-out daily chest request, guest player/account IDs, reward nonce/hash, per-device counts/cooldowns and expiry, unchanged signed-in/modern rewards, captured gauntlet membership/order/hash, downloads of all five levels, malformed and inaccessible gauntlets, signed-in/anonymous quest responses, empty and partial quest configuration, nonce/hash validation and UTC rollover, 2.1 anonymous votes/uploads with placeholder credentials, the captured signed-in comment dislike after an existing native vote, rejection of invalid authenticated credentials, all four captured 2.01 request shapes, version-20 storage/search/download, same-name revisions and repair of an incorrect tag, distinct-name new uploads, World detection, HTTPS-only plaintext account operations across versions, rejection of forged forwarding headers, the captured 1.9 star-rating request with all ten rating values, the captured double-slash dislike request after an existing vote, visibility through modern level/comment endpoints, anonymous action quotas and comment spam state, the exact sparse 1.0/1.4 vote forms, all five face-rating conversions, duplicate votes, level/comment likes and dislikes, zero-star leaderboards, device-based relative leaderboards, credential failures, preservation of newer stats, raw/zlib uploads and download hashes, old search pagination and OR filters, gauntlet filtering, comment formats, persistent isolated guests, inbox privacy and read state, modern inbox passthrough, backups, concurrent request isolation, and first-registration permissions. Protocol fixtures cover pre-1.9, 1.9, 2.0-style routes, 2.1, and modern passthrough. Actual game binaries and a running Express deployment have not been tested here.

The HTTPS regression is automatically skipped while its guard is commented out locally for client testing. Uncommenting the existing guard enables that check again; the test runner does not alter the plugin or enable the guard.
